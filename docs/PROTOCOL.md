# Исследование протокола Simple Voice Chat

> **Статус:** исследование и проектное ограничение, а не спецификация для несанкционированных клиентов.  
> **Проверенная исходная база:** официальный репозиторий `henkelmax/simple-voice-chat`, ветка `26.2`, просмотренный снимок от 2026-08-21. [1]

## Назначение документа

Этот документ фиксирует то, что было подтверждено по актуальному исходному коду и официальному API Simple Voice Chat (SVC), прежде чем создавать сетевой клиент. Его главная цель — не допустить подмены личности, угадывания секретов, обхода прав доступа или реализации неподтверждённого протокола.

| Вопрос | Подтверждённый вывод |
|---|---|
| Достаточно ли для подключения IP и UDP-порта? | **Нет.** Обычный клиент сначала получает сессионные bootstrap-данные через Minecraft-соединение. |
| Можно ли создавать UUID или ключ на стороне standalone-клиента? | **Нет.** Секрет должен быть выдан сервером для конкретной личности; подделка нарушает модель SVC. |
| Является ли UDP-протокол публичным стабильным API? | **Нет.** Это внутренняя реализация; её нужно изолировать за версионным адаптером и проверять интеграционными тестами. |
| Поддерживает ли публичный API Paper выпуск данных для внешнего UDP-клиента? | **Нет.** Устаревший `VoicechatServerApi#getSecret(UUID)` документирован как возвращающий `null`. |
| Возможен ли полноценный независимый клиент исключительно через public API? | На проверенной версии — **не подтверждено и не реализуется**: public API не предоставляет нужного безопасного bootstrap-контракта. |

## Жизненный цикл обычного клиента

Обычный Minecraft-клиент не начинает голосовой сеанс простым UDP-запросом. После совместимости клиента и сервера он отправляет игровому серверу `RequestSecretPacket`. Сервер создаёт/получает секрет для UUID игрока и направляет `SecretPacket` через Minecraft custom payload. В нём находятся, в частности, сессионный секрет, UUID, голосовой host/port, выбранный codec, MTU, keep-alive, флаг групп и параметры дальности.

После получения этих данных UDP-клиент направляет `AuthenticatePacket`, содержащий UUID и секрет. Сервер сопоставляет их со своей внутренней таблицей секретов. После `AuthenticateAckPacket` клиент передаёт `ConnectionCheckPacket`; только после его обработки сервер переводит подключение из непроверенных в активные. Этот путь прослеживается в `ClientManager`, `InitializationData`, `ClientVoicechatConnection`, `Server`, `ServerVoiceEvents` и `SecretPacket` официального исходного дерева. [1]

> **Критическое следствие.** Режим «Voice Chat address» допустим лишь как транспортный адрес **после** успешного законного bootstrap. Сам по себе IP:UDP-порт не несёт ни идентичности, ни секрета, ни согласованных параметров.

## Транспорт и защита данных

В проверенной реализации UDP-фрейм клиента содержит magic byte, UUID отправителя и массив зашифрованной полезной нагрузки. После расшифровки полезная нагрузка начинается с ID внутреннего пакета. Класс `Secret` использует AES-GCM с новым случайным IV для каждого зашифрованного payload; IV добавляется к ciphertext. Внутренние идентификаторы и бинарные детали намеренно не дублируются в продуктовой документации как публичный контракт.

Ключевой материал нельзя писать в UI, обычный лог или отчёт об аварии. В приложении секрет должен размещаться в короткоживущем объекте сессии, не сохраняться в конфигурации, очищаться при disconnect и не попадать в исключения или телеметрию.

| Компонент | Обязанность приложения |
|---|---|
| UDP transport | Тайм-аут, IPv4/IPv6-диагностика, отмена через `CancellationToken`, ограничение размера datagram. |
| Session secret | Принимать только от легитимного, явно поддерживаемого server-side bootstrap, не сохранять. |
| Packet codec | Прятать за `ISvcProtocolAdapter`; не связывать с Avalonia UI. |
| Cryptography | Использовать ровно подтверждённый механизм версии сервера; не ослаблять, не заменять и не отключать аутентификацию. |

## Аудиоконтур

Официальный клиент использует Opus-кодирование для голосовых фреймов, а полученные sound-пакеты декодирует с компенсацией пропусков и воспроизводит в аудиоканале. Это подтверждается `MicThread`, `AudioChannel` и API-интерфейсами `OpusEncoder` / `OpusDecoder`. [1]

В будущих реализациях (.NET и Android/Kotlin) аудиоконтур должен быть разделён на `IAudioCapture`, `IOpusCodec`, `ISvcAudioPacketCodec` и `IAudioPlayback`. Захваченный PCM никогда не передаётся по сети напрямую: до UDP он должен быть кодирован в Opus и инкапсулирован только подтверждённым адаптером текущей версии SVC.

## Группы и игровые custom payload

Метаданные групп и команды join/leave обычного клиента проходят по каналу Minecraft custom payload, а не по самостоятельному публичному UDP API. Это видно по `AddGroupPacket`, `RemoveGroupPacket`, `JoinGroupPacket`, `LeaveGroupPacket`, `JoinedGroupPacket`, `NetManager` и `ServerGroupManager` в исходном коде. [1]

Публичный серверный API может получать серверные группы и менять группу уже существующего `VoicechatConnection`, но не создаёт внешнее голосовое подключение для произвольного standalone-клиента. В частности, публичный `getSecret(UUID)` устарел и его контракт сообщает, что он возвращает `null`. Следовательно, список групп или операция входа не должны эмулироваться и не должны обходить пароль, приватность или permissions.

## Решение по Paper bridge

### Что необходимо

Для законного standalone-сеанса (Windows или Android) сервер должен иметь **официально поддержанный** путь для:

1. Надёжной аутентификации конечного пользователя, выбранной владельцем сервера.
2. Связывания этого пользователя с разрешённой серверной личностью.
3. Создания и выдачи короткоживущих bootstrap-данных SVC без раскрытия долгоживущих секретов.
4. Синхронизации разрешённого списка групп и операций join/leave без нарушения прав.

### Что подтверждено API

Paper-плагин может легитимно зависеть от `voicechat`, зарегистрировать `VoicechatPlugin` через `BukkitVoicechatService` и получить `VoicechatApi` в `initialize`. [2] [3] Это требуется для обычной интеграции с SVC.

### Что API не предоставляет

На исследованной версии public API отсутствует поддерживаемый метод выдачи рабочего UDP bootstrap для нового внешнего клиента. Использование внутренних классов `Server`, `Secret` или `SecretPacket` для обхода этого ограничения нарушило бы требование опираться на public API и сделало бы проект хрупким при обновлении SVC.

Поэтому `StandaloneVoiceBridge` в этом репозитории будет создан как **fail-closed заготовка интеграции**: он корректно стартует на Paper, проверяет наличие SVC и сообщает, что выдача standalone-сессий выключена, пока upstream не предоставит официальный extension point либо сервер не подключит одобренную реализацию bootstrap-провайдера. Он не будет выдавать фиктивные секреты или создавать поддельные подключения.

## Требования к версии и тестированию

Поддержка нескольких версий строится через `ISvcProtocolAdapter` и независимый `ProtocolVersion`. Нельзя заявлять совместимость, пока тестовый Paper+SVC сервер не подтвердит handshake, обмен аудио и группы с конкретной release-версией.

Минимальные автоматические проверки должны покрывать сериализацию DTO, machine состояний, очистку секретов, тайм-ауты, backoff reconnect и запрет на вызовы неподдерживаемого bootstrap. Интеграционные тесты с реальным сервером необходимы до включения реального аудиотрафика.

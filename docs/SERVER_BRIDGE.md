# Standalone Voice Bridge

Этот документ описывает проект легитимного серверного моста (Paper Plugin) для безопасного подключения внешних (Standalone) клиентов к Simple Voice Chat.

## Почему не работает прямое подключение?

Как описано в [PROTOCOL.md](PROTOCOL.md), обычный клиент Minecraft не может начать UDP-сессию, просто зная IP и порт. Для подключения необходимы:
1. **Идентичность (UUID)** — уникальный идентификатор игрока, признанный сервером.
2. **Секрет (Secret)** — короткоживущий криптографический ключ, выданный сервером для конкретной сессии.
3. **Параметры сессии** — кодек, MTU, флаги групп, которые сервер согласовывает с клиентом.

В официальном клиенте эти данные передаются по защищенному каналу Minecraft (Custom Payload) в пакете `SecretPacket`. Публичный API Simple Voice Chat (версия 2.6.x) намеренно не предоставляет способа запросить этот секрет извне, чтобы предотвратить подмену личности и несанкционированный доступ.

## Архитектура безопасного моста

Чтобы standalone-клиенты (Windows и Android) могли работать, серверный плагин должен выполнять роль доверенного посредника, не нарушая модель безопасности SVC.

### 1. Аутентификация

Мост не должен создавать выдуманные UUID. Он должен использовать легитимный механизм аутентификации, например:
- **Связывание с Discord/Web-аккаунтом:** Игрок привязывает свой Minecraft-аккаунт к внешнему сервису. Standalone-клиент авторизуется через этот сервис (например, OAuth2), а мост проверяет токен.
- **Одноразовые коды (OTP):** Игрок заходит на сервер через обычный Minecraft-клиент, вводит команду `/voice auth`, получает временный код и вводит его в Standalone-клиенте.

### 2. Выдача секрета (Bootstrap)

После успешной аутентификации мост должен запросить у SVC секрет для подтвержденного UUID.
Поскольку `VoicechatServerApi#getSecret(UUID)` возвращает `null`, мосту потребуется использовать внутренние классы SVC (рефлексию или прямое обращение к `de.maxhenkel.voicechat.voice.server.Server`), что делает плагин зависимым от конкретной версии SVC.

**Процесс:**
1. Standalone-клиент подключается к API моста (например, по TCP/WebSockets).
2. Клиент проходит аутентификацию.
3. Мост получает экземпляр внутреннего сервера SVC.
4. Мост вызывает `server.generateNewSecret(uuid)`.
5. Мост отправляет клиенту параметры (UUID, Secret, Host, Port, Codec, MTU).
6. Клиент разрывает TCP-соединение и начинает стандартный UDP-handshake SVC.

### 3. Интеграция в мир (Виртуальный игрок)

SVC требует, чтобы игрок находился в мире (имел координаты), чтобы работал пространственный звук (Positional Audio). Если Standalone-клиент подключается без запущенного Minecraft, на сервере нет сущности игрока.
- Для **глобальных групп** это не проблема (звук не позиционируется).
- Для **пространственного звука** мосту придется либо создавать "виртуального" игрока (NPC), либо привязывать аудио к конкретной локации (например, лобби).

## Текущая реализация (Fail-Closed)

В репозитории подготовлен каркас плагина `paper-plugin`. На данный момент он **намеренно отключен (fail-closed)**.
Он регистрируется в API SVC, но не открывает внешние порты и не выдает секреты, так как:
1. Использование внутренних классов (рефлексии) нарушает гарантии стабильности API.
2. Без механизма аутентификации (например, OTP) выдача секретов по запросу создаст критическую уязвимость на сервере (любой сможет подключиться под чужим UUID).

## Дальнейшие шаги

Для превращения каркаса в рабочий мост необходимо:
1. Выбрать и реализовать механизм аутентификации (OTP через команду `/voice standalone`).
2. Написать адаптер версий для доступа к внутреннему методу `generateNewSecret`.
3. Реализовать безопасный TCP-канал для передачи Bootstrap-данных от плагина к Standalone-клиенту.
4. Обновить `ISvcProtocolAdapter` в клиентах для поддержки этого нового TCP-канала.
